The only exceptions: full-bleed backgrounds (the content still stays inside the container), the phone number in the header, wide tables that scroll sideways on phone, and the sticky header. Nothing else is allowed to leave the system.

BREAKPOINTS

Two lines that change the layout, six states we check

A breakpoint is where the layout is allowed to change; between breakpoints it only stretches. We use Tailwind's built-in lines and nothing custom. Two of them change the layout: 640 (phone → tablet: 2 columns, gutter 32) and 1024 (tablet → laptop: full nav, header 72, 3 or 4 columns, two-column layouts split). Those give the three core states we design: phone, tablet, laptop. Three supporting states come with the template and need no design: small-phone fixes below 380, the header phone number from 1536 (desktop), and the container growing to 1440 from 1650 (extra wide). 768 and 1280 exist in Tailwind but nothing changes there. For comparison, Superside works with 768, 1024, 1280 and 1650 plus a 360 line; designindc.com (Bricks) with 768 and 992 plus 360. The dots under the ruler are the one width we check for each state.

Why those devices. StatCounter US, Aug 2025 to Aug 2026: phones 414 × 896 (iPhone 11, 14%), 390 × 844 (iPhone 12 to 14, 13%), 393 × 852 (iPhone 15 / 16, 7%), 375 × 812 (SE / mini, 7%); tablets 768 × 1024 (older iPad, 11%), 820 × 1180 (iPad 10th gen / Air, 10%); desktops 1920 × 1080 (26%), 1536 × 864 (15.6" Windows laptop at 125%, 7%), 1366 × 768 (5%), 1440 × 900 (MacBook Air 13", 4%). Our clients are US businesses whose marketing teams are on Apple hardware, so we check on Apple devices wherever one sits in the range: iPhone SE (375 × 667), iPhone 14 (390 × 844; the newer 15 / 16 at 393 × 852 behave the same), iPad Air 11" (820 × 1180), MacBook Air 13" (1440 × 900; the M2 / M3 Air default of 1470 × 956 lands in the same state) and MacBook Pro 16" (1728 × 1117, the same state a 1920 Full HD monitor lands in). The one exception is the desktop state, 1536 to 1649, where no Apple screen sits; the 15.6" Windows laptop at 1536 × 864 is the most common real device there. All sizes are CSS pixels at the device's default scaling. Screen is the whole display; viewport is what the page actually gets on first load once the browser's own bars are taken off (iOS Safari: status bar, address bar and bottom toolbar; macOS: menu bar plus Chrome's tab and address bars; Windows: taskbar plus Chrome's bars). Phones and iPads gain 75 to 90px once Safari collapses its bars on scroll. The previews use the viewport, not the screen.

Three core states you design for: phone, tablet, laptop. Three supporting states come with the template and need no design of their own: small-phone fixes below 380, the desktop phone number from 1536, and the wider container from 1650. Nobody designs for the supporting ones; the nearest core design simply adjusts. A MacBook Air or Pro (1440 to 1728 wide) is a laptop; only a 16" Pro at 1728 crosses into the desktop row, where all it gains is the phone number.

CONTAINER AND GUTTERS

One box, always centred, always the same edges

The container is the width the content lives in: 1240 in the laptop and desktop states, 1440 in extra wide. Below 1320px it gives way to a fixed gutter. Above it the leftover space splits evenly on both sides. The important part is not the number, it is that the logo, the header button, the H1 and the images all sit on the same two lines at every width.

VERTICAL RHYTHM

Spacing between sections, and inside them

Good sites feel calm because the vertical spacing comes from one scale and repeats. Ours is built on 8px. Sections carry their own padding top and bottom, backgrounds do the separating, and nothing else adds space between them. Measured for reference: designindc.com runs 78 laptop / 50 phone, CiviClick 96 / 40, Superside about 96 / 48. We sit in the middle at 80 / 64 / 56, which reads generous on a laptop without turning phones into scrolling white space.

THE SIX RULES
Sections own their padding. 80 / 64 / 56 top and bottom. Nothing adds margin between sections.
Backgrounds divide. Alternate white and grey (or dark) to separate blocks. Two same-colour neighbours get a 1px hairline.
Heroes are bigger. 96 / 64 / 48, and the home hero may use display type.
Heading block, then content, then action. 12 · 16 · 40 · 32, as drawn.
Phone is 70%, not 50%. 80 → 56 keeps the rhythm without the page feeling cramped.
Same block, same spacing, every page. A card grid on the About page is spaced exactly like the one on Home.

CODING PRINCIPLES

How the wireframe becomes the live site without being rebuilt

The goal of the process: the client approves the wireframe content, we add design on top of the same code, and that code goes live with Payload underneath. That only works if the wireframe is written as production code from day one. These rules come out of three reviews: the Meyer port (captured HTML, nothing reusable), the Meyer Payload layer (right work on the wrong base) and the designindc.com inner pages (good architecture, drifting details). Each rule says what we saw, what to do, and how to check it.

1. One pipeline, one codebase
RULE

The wireframe is built in the real stack (Next.js, Tailwind, our tokens) with grey placeholders. Hi-fi changes tokens, images and motion on the same files. Payload is wired to the same components at the end. Nobody rebuilds anything at any stage.

WHY, AND HOW TO CHECK

Meyer was rebuilt three times because each stage started from a different base. Check: the hi-fi commit touches globals.css, images and a few components, never page files. If a page file needs rewriting for hi-fi, the wireframe was not production code.

2. Tokens, never values
RULE

Every colour, font size, spacing and radius is a token in :root. Components use var(--brand) or bg-brand, never bg-[#3d4adf]. Wireframes ship with grey tokens; hi-fi swaps the values, not the components.

WHY, AND HOW TO CHECK

designindc inner pages: 109 hex colours in templates while the same colours existed as tokens; two different whites on one site. Check: grep -r "#[0-9a-f]\{6\}" src/components src/templates returns nothing. Arbitrary values like pt-[10.8125rem] are a smell.

3. One component per thing, variants as props
RULE

Same skeleton, different content: one component with a variant prop. Different skeleton: a second component built from the same parts. Copying a file and editing it is never allowed.

WHY, AND HOW TO CHECK

Six hero files on designindc with the same padding and grid; 45 hand-rolled section headings with five different gaps. Check: heading + intro, hero, card, CTA band, lead form each exist exactly once in components/. If a change to H2 size needs more than one edit, there is a copy somewhere.

4. Names describe the thing, not the page
RULE

The default gets the plain name (Hero, Card, SectionHeading). A different arrangement gets the plain name plus what differs (HeroForm, CardPricing). Variants are props. No page, client or project names on components.

WHY, AND HOW TO CHECK

AboutHero is wrong the day Talent uses it. Check: no component file is named after a route. Files sort into families in the folder (Hero, HeroForm, HeroDark).

5. Routes are thin, content is data

Three things live in three places: the URL, the layout, and the words. Keeping them apart is what makes content edits safe right up to launch.

LAYER	FILE	OWNS	WHO EDITS IT
Route	app/about/page.tsx	"/about/ exists, use AboutPage, set the title". Under 20 lines.	developer, once
Template	templates/AboutPage.tsx	which blocks, in which order, with which variant	developer / designer in hi-fi
Components	components/Hero.tsx	how any hero looks; receives words and images as inputs, never contains them	developer / designer in hi-fi
Content	content/about.ts (or JSON)	the words, links and image paths the client approved	anyone, any time, including the studio agent

Change the URL: touch the route. Change the design: touch components and tokens. Change the words: touch the content file. Nothing else moves.

RULE

No sentence of client copy inside a .tsx file. Labels like "Read more" are fine; "Meyer ships three times the units of any rival" is not. Content files stay flat and readable: heading, text, cta: {label, href}, items: [...]. If a designer cannot open the file and see which line is which sentence on the page, it is too clever.

WHY, AND HOW TO CHECK

This is what made the Payload layer on Meyer a one-day job and what designindc did right. The client-approved wireframe copy becomes a file we can diff and send; Payload seeds from it later. Check: grep a sentence from the approved copy; it must be found in content/, never in components/ or templates/.

LAST-MINUTE CONTENT CHANGES DURING HI-FI (THEY ALWAYS HAPPEN)
CHANGE AT 5PM	WORDS INSIDE COMPONENTS	WORDS IN CONTENT FILES
Typo in the About headline	open Hero.tsx, find the string in the markup, edit, hope the layout survived	edit one line in content/about.ts
Client sends 12 copy changes	12 files across the codebase, needs a developer	one or two text files; a designer or the studio agent can do it
Swap a photo	find the <img> in the component	change one path
Add a fourth value to a list	edit JSX, add markup	add an item; the component renders it
"What changed since approval?"	read React diffs	diff one text file, readable by a human

The rule is not "content is frozen". It is "content lives where changing it is safe and cheap". In the Design Studio, "change the About headline to X" becomes a one-line edit the agent can make without touching a component, and the preview updates at once. When Payload goes on, the same files seed the CMS and the client makes the late changes themselves in the admin, same fields, no re-entry.

6. The layout rules are code, not a PDF
RULE

Container 1240, gutters 20 / 32 / 40, sections 80 / 64 / 56, breakpoints at 640 and 1024, spacing on the 8px scale, type scale as plain CSS classes. All of it lives in globals.css as tokens and utilities (.container, .section, .t-h1), and components use those, never their own numbers.

WHY, AND HOW TO CHECK

Meyer's H1 rendered at 25px and its logo at the wrong size because sizes were set in ways that silently failed. Check with a browser, not by reading: measure container, gutter, header, logo and H1 at 390 / 834 / 1440 on every template, and the numbers must match the guide.

7. Base styles go in @layer base
RULE

Any element rule in the global stylesheet (img, h1, a) sits inside @layer base. Unlayered CSS beats every Tailwind utility, so one innocent line can override the whole site.

WHY, AND HOW TO CHECK

An unlayered img { height: auto } silently cancelled Meyer's logo height. Check: no bare element selectors outside @layer blocks in globals.css.

8. Match the design, never the code
RULE

When a site is rebuilt from WordPress, Bricks or anything else, the old HTML and CSS are reference only. We read the live site for content, tokens and layout, and build our own components. No captured markup, no dangerouslySetInnerHTML, no copied stylesheet.

WHY, AND HOW TO CHECK

The Meyer port carried a 1.25MB site.css and could not be edited. Check: grep -r dangerouslySetInnerHTML src finds only JSON-LD script tags; no file in public/ came from the old site's theme.

9. Phone, tablet, laptop: three core states, designed and tested
RULE

Every component is built for all three core states at once, not laptop first and patched later. Images come first in stacked layouts. Tap targets 44px. Wide tables scroll inside their card. Checked on all six state devices: 375, 390, 820, 1440, 1536, 1728.

WHY, AND HOW TO CHECK

designindc's Contact page overflows sideways at 390 because one laptop-only padding rule had no phone counterpart. Check: an automated pass over every route at 390 and 1440 reports zero horizontal overflow, zero console errors, zero broken images. It runs before every review link is sent.

10. Content is reviewable
RULE

New or changed copy is marked in code (data-new) and can be shown in red with a switch. Every inline link from the client's copy is kept. Nothing is invented: no logos, no claims, no headings that were not in the source.

WHY, AND HOW TO CHECK

Clients approve wireframes for content; they must see exactly what changed. Check: the review switch shows every new sentence, and a link audit script finds every inline link from the source in the build.

11. Git from the first hour, production build for every link
RULE

Every project is a git repository before the first component exists, with small commits. Review links are served from next build + next start, never from the dev server behind a tunnel. Nothing else runs on the review host.

WHY, AND HOW TO CHECK

designindc's 26 pages were unversioned; Meyer's dev server did not hydrate through the tunnel and every button was dead. Check: git log shows daily history; the service unit says next start.

12. Payload last, on approved components
RULE

The CMS goes on after the design is approved, on the same components, reading the same data shapes the wireframe used. One collection per content type, one global per standing page, uploads for pictures, migrations only. Slugs read-only.

WHY, AND HOW TO CHECK

Payload on an unapproved design doubles every later change. Check: the Payload commit adds collections, globals and a data loader; it does not touch component markup. An edit in the admin shows on the page; a CMS outage still renders the shipped copy.

The one-line version. Write the wireframe as if it is going live tomorrow, because it is: tokens not values, one component per thing, content in data, layout rules in code, measured in a browser, committed to git.
